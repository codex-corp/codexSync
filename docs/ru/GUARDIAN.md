# Хранитель снимков

[English](../en/GUARDIAN.md) · **Русский** · [中文](../zh/GUARDIAN.md)

[← Документация](README.md)

Codex хранит проекты и привязки чатов в `.codex-global-state.json`. Если Codex
упадёт, пропадёт питание или случится BSOD во время записи этого файла, он может
оказаться обрезанным или пустым — а вместе с ним пропадут все проекты.

Хранитель — единственная часть codexSync, которая работает **при открытом
Codex**. Он только читает файл и пишет проверенные снимки в собственный
каталог, который конфигурация обязана расположить вне `.codex`, зеркала,
резервных копий и temp. В окне это экран
[«Хранитель снимков»](GUI.md#хранитель-снимков).

## Команды

```powershell
codexsync -c config.toml guardian snapshot --once   # снять один снимок сейчас
codexsync -c config.toml guardian watch             # снимать снимки, пока работает Codex
codexsync -c config.toml guardian list              # снимки и карантин; ничего не записывает
```

Чтобы снимать снимки по расписанию, задайте `[scheduler] mode =
"guardian_snapshot"` и выполните `automation apply` (см.
[Автоматизация](CONFIGURATION.md#автоматизация)).

## Как принимается решение о снимке

- **Устойчивые чтения.** Файл должен прочитаться одинаково несколько раз подряд
  (`stable_reads`, по умолчанию 3), поэтому состояние, пойманное посреди записи,
  снимком не станет. `watch` опрашивает файл каждые 3 с, ждёт 2 с после
  изменения и раз в 60 с делает резервный обход на случай пропущенного
  изменения.
- **Проверка.** Проверяются байты, JSON и ссылочная целостность: NUL-байты, BOM
  (кроме одной метки UTF-8 в самом начале файла), повторяющиеся ключи, привязки к
  несуществующему проекту.
- **Схема распознаётся, а не предполагается.** У каждой известной формы файла
  свой адаптер; состоянию, которое не распознал ни один адаптер, хранитель не
  доверяет.
- **Подозрительное сокращение.** Состояние, потерявшее много проектов или
  привязок по сравнению с последним хорошим снимком, уходит в **карантин**, а не
  заменяет его (`shrink_min_count`, `shrink_ratio`). Пока Codex переписывает такое
  состояние, карантин хранит два события на одну потерю — первое и самое новое,
  которое считает перезаписи между ними, — а не копию каждой перезаписи.
- **Порядок и видимость.** Снимки упорядочены монотонным поколением, а не
  часами; новый снимок получает номер больше всех снимков хранилища, а файл
  снимка, который в этот момент не читается, останавливает фиксацию, пока не
  станет читаемым. Снимок виден только после `COMMITTED`, и ничто подозрительное
  не может стать `latest-good`. Папка, которую сбой оставил без `COMMITTED`,
  удаляется через `staging_retention_hours`.
- **Ошибка хранилища не останавливает `watch`.** Снимок, занятый другой
  программой, или полный диск стоят одной попытки: `watch` пишет это в журнал,
  ждёт с каждым разом дольше и пробует снова.

Честное ограничение: `snapshot --once` по расписанию не гарантирует, что снимок
будет свежим в момент BSOD. Он гарантирует, что существующий снимок цел и
пригоден для восстановления.

## Восстановление из снимка

Возврат снимка начинается с предпросмотра: сколько проектов и привязок в
состоянии сейчас и сколько станет. Восстановление требует закрытого Codex и
точного id плана и пишет через тот же конверт, что и любая правка глобального
состояния: блокировка операции, журнал, проверенная резервная копия заменяемого
файла, финальная проверка процесса и проверенный откат, если после замены что-то
пошло не так.

```powershell
codexsync -c config.toml guardian restore --snapshot <snapshot-id>
codexsync -c config.toml guardian restore --snapshot <snapshot-id> --confirm <plan-id> --dry-run
codexsync -c config.toml guardian restore --snapshot <snapshot-id> --confirm <plan-id>
```

Отклоняются: снимок, который больше не проходит проверку; снимок другой машины;
снимок в другой схеме, чем файл, который Codex пишет сегодня; живой файл, в
котором состояние проектов записано в форме, которую codexSync ещё не распознаёт
(`LIVE_SCHEMA_UNKNOWN` — это более новый Codex, а не повреждение); восстановление,
когда живого файла нет.

Восстановление старого снимка не отматывает хранитель назад: следующий снимок
восстановленного файла — новое поколение, и он становится `latest-good`.

## Новая база

Хранитель сравнивает каждое состояние с `latest-good`. Если потеря проектов или
привязок **настоящая** — например, Codex пересоздал проекты под новыми id, —
каждое следующее состояние всё равно сравнивается с базой до потери, и
`latest-good` больше не сдвинется никогда. `doctor` предупреждает, когда это
произошло.

`guardian accept` объясняет сокращение только числами: сколько проектов
пересоздано под новым id, удалено или добавлено и на какие из них указывали
потерянные привязки. С `--confirm` текущее состояние фиксируется как
`latest-good`.

```powershell
codexsync -c config.toml guardian accept
codexsync -c config.toml guardian accept --confirm <plan-id>
```

- Принять можно только сокращение, но не состояние, которое не проходит
  проверку, — или **смену схемы**: если состояние записано в другой известной
  схеме, чем база (новая сборка Codex, база старше учёта схем), хранитель не может
  их сравнить и задерживает каждое состояние. Такое состояние можно принять, если
  оно проходит все проверки в своей схеме (`BASELINE_SCHEMA_CHANGED`).
- Id плана закрепляет само сокращение, а не байты файла, поэтому его можно
  подтвердить, пока Codex продолжает переписывать файл.
- Снимок помечается `SHRINK_ACCEPTED` (или `SCHEMA_CHANGE_ACCEPTED`), и хранение
  не удаляет ни его, ни перекрытую им базу ([D-014](../dev/DECISIONS.md)).

## Настройки

```toml
[guardian]
root_dir = "${workspace_root}/guardian"   # вне .codex, зеркала, резервных копий и temp
max_state_bytes = 67108864                # наибольшее допустимое состояние (1 МиБ – 1 ГиБ)
shrink_min_count = 2                      # сокращение подозрительно, если потеряно не меньше стольких элементов…
shrink_ratio = 0.25                       # …и не меньше такой их доли
retention_days = 30                       # 0 отключает ограничение
max_snapshots = 100                       # 0 отключает ограничение
quarantine_retention_days = 30
staging_retention_hours = 24
poll_interval_seconds = 3
debounce_seconds = 2
stable_reads = 3
stable_read_interval_seconds = 0.5
fallback_scan_seconds = 60
once_timeout_seconds = 120
```
